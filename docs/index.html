Sokoban Solver Field Notes

What happened to the Rust solver in ~/sokoban-ai: which ideas went in and why, which were measured and thrown out, and where each piece lives in the code. On SokHard it went from 61 to 116 of 163 levels at 10 seconds, level with YASS on the same machine.

github.com/rkirov/sokoban-ai Code pointers link to commit 2350191 24 commits since the July baseline ~5,700 lines of Rust in src/ 36 tests

At a glance

The solver races four searches in parallel threads and reports the first solution that replays correctly. The main work of the September sessions was:

  • FESS rewrite. A new feature-space search over macro moves, guided by packing plans computed backward from the goal. This took XSokoban from 16 to 67 solved.
  • Exact small deadlock tables. Tables for pairs and triples of boxes, in both push and pull directions, plus a fast filter that skips most lookups. This took SokHard from 61 to 98.
  • Faster backward search. A second, weighted backward thread, warm-started matchings and cheap dual lower bounds. This took SokHard from about 100 to 116.
  • Safety. Only a verified solution can stop the race, a memory watchdog caps each run, and EXPERIMENTS.md records every technique tried, kept or not.

How it unfolded

  1. 2 July 2026 · baseline

    The first session produced a racing portfolio: forward A* with a matching lower bound, bidirectional search, weighted A*, and a unit-push FESS. Pruning included freeze deadlocks, PI-corrals and a corral mini-search, with CI and verified LURD output. Starting scores at 10 s: Microban 480/493, XSokoban 16/90, SokHard 61/163.

  2. 27 Sep · review and bug hunt

    A review from first principles found three real bugs. The backward search merged mirror-image states, the corral verdict cache ignored the region, and naive tunnel macros were unsound (that one had already been caught in July). An early session crash led to a 3 GB cgroup cap on every benchmark run and one-at-a-time CPU jobs.

  3. 28 Sep · FESS rebuilt

    FESS was rewritten over macro moves, with goal-cluster packing layers, exact consistent-filling tables, a relaxed backward plan for parking, hotspots and frozen-box walls. XSokoban went from 16 to 63, then 67.

  4. 28 Sep · deadlock tables

    Exact pair and triple tables were added, forward and backward, plus gate pushes and partner filtering. SokHard went from 61 to 98. Commit 85dba28 landed the bulk, and 05a27cb added partner filtering.

  5. 28–29 Sep · portfolio reshaped

    Bidirectional search (500 lines) was removed: weighted backward search replaced it with no loss on any pack. The default became optimal A*, FESS, backward, and weighted backward (f33c8df, 9ca54ac).

  6. 29 Sep · backward engine

    The backward search got warm-started matchings (752d5fe), compact matching storage (e608282), and O(m) dual bounds for children (c896c41). SokHard reached 115–117, level with YASS's 117.

  7. 29 Sep · calibration and ideas

    60-second runs showed which packs are time-bound (SokHard) and which need smarter search (XSokoban, Sasquatch). Codex was asked for novel ideas. Two were kept, and the others were measured and rejected. Player-aware distances were mid-measurement when the work was paused.

Sokoban for solvers

A position is the set of box squares plus the player's position. Two positions where the player can walk between the same squares behave identically, so the solver names the player by the smallest square index of its reachable region. That pair (sorted boxes, region name) is the transposition-table key everywhere.

The unit of cost is a push. Walking is free and is reconstructed afterwards (src/verify.rs:13 pushes_to_moves), then the full move string is replayed against the original level text (src/verify.rs:91) before anything is reported.

Three ideas carry most of the weight:

  • Lower bounds. An optimistic estimate of pushes remaining, used to order A* and to prove positions dead when it is infinite.
  • Deadlocks. Positions that can never be solved. Every one detected removes a whole subtree.
  • Search shape. Which positions to look at first. Most hard levels are lost here, not to raw speed.

Below is the solver's actual solution to XSokoban #1, 97 pushes found in 31 ms, replayed move by move. Lowercase letters in the output are walks and uppercase are pushes.

Board precomputation

Each goal gets a table of relaxed push distances: how many pushes a lone box needs to reach it, when the player can teleport to any floor square. The search runs backward from the goal as pulls. A box at q can be pulled to neighbour n when n and the square beyond it are floor. Squares no goal can be reached from are dead, and no push onto them is ever generated.

Player-aware distances (parked experiment)

The relaxation above ignores where the player can actually walk. After a push the player stands where the box was, and can only reach the box sides that connect to that square without going through the box. The branch player-aware-dists tracks (box square, player-side component) states instead.

The bound stays a lower bound, and it can only get tighter. On SokHard it changes the tables on 70 of 163 levels and finds new dead squares on 27. The two boards below are computed in the browser with both rules.

Gate pushes

Suppose a box is pushed onto a non-goal square that cuts the pusher's side off from the box's other sides, using walls alone. Then the only useful next move for that box is to keep pushing it forward. This is a property of the position alone, so it is safe to use with a transposition table. Naive tunnel macros, which force boxes through wall-flanked runs, are not safe: Microban 1 #10 below needs a box parked inside such a corridor. The test src/tests.rs:195 tunnel_parking_is_required pins this.

A* and the matching bound

Forward A* over pushes orders positions by g + h. Here h is a minimum-cost matching of boxes to goals over the distance tables, solved with the Hungarian algorithm. If no perfect matching exists, some box can reach no free goal and the position is dead. The search materializes children lazily: queue entries are (parent, box, direction), and a child is built and checked only when popped.

src/solver.rs:162 solvesrc/solver.rs:111 BucketQueuesrc/matching.rs:72 solvesrc/matching.rs:161 resolve_row

Two engine facts matter:

  • Bucket open list. Keys are small integers (f, then h), so an array of buckets replaces the binary heap. It keeps the same order and identical node counts, runs 10–15% faster, and uses queue entries four times smaller.
  • One-row updates. A push changes one box, so one row of the cost matrix. The matcher re-augments a single row from the parent's solution (O(m²)) instead of solving from scratch (O(m³)). This is exact only if rectangular problems are padded to square with zero-cost dummy rows; a property test pins that.

With frozen boxes on goals, FrozenWalls recomputes distances treating them as walls, cached per frozen set. That catches the common stall where every box but one is packed and the last goal is sealed off.

Backward search

The backward search starts from the solved position and pulls boxes, looking for the start position. Cramped goal rooms, hard to fill forward, are easy to empty backward. It uses the mirror tables: start_dist for the bound and backward dead-set tables seeded from the start squares.

It became the SokHard workhorse. In a 60 s calibration, 48 of the 66 extra levels were solved by a backward thread. So its speed was worth engineering, and it now runs twice in the portfolio: optimal (w = 1), and weighted f = g + 3h, because the two orderings solve different levels.

What happens when an entry is popped

  1. Materialize. Copy the parent's boxes in parent order, move one box. Keeping the parent's order means matching row i is still box i, which the warm start needs. A sorted copy is used for the key.
  2. Flood the player region and name it by its smallest square.
  3. Duplicate check in the transposition table (60–70% of pops on hard SokHard levels are duplicates).
  4. Exact bound. Load the parent's saved matching (column potentials plus assignment; row potentials are recomputed from complementary slackness) and re-solve the one changed row.
  5. Requeue if the bound rose. Children were queued with a cheaper lower bound, and if the exact value is higher the entry goes back in at its true key. Nothing is stored yet, so this is cheap.
  6. Store and expand. Save the matching state for this node's children, test for the start position, generate pulls, filter by backward dead squares and dead sets, and queue each child with its O(m) dual bound.

The O(m) dual bound

For each child, a full re-solve would cost O(m²). Instead, keep the parent's dual solution (u, v) and replace only the moved row's potential by that row's minimum reduced cost. The duals stay feasible, and by weak duality any feasible dual objective is a lower bound on the new optimum.

// src/matching.rs:134  LB = total − u_r + min_j (c'_rj − v_j)
pub fn row_lower_bound(&self, r0: usize, total: u64, cost: impl Fn(usize, usize) -> Option<u32>) -> Option<u64> {
    let r = r0 + 1;
    let mut best = i64::MAX;
    for j in 1..=self.m {
        if let Some(c) = cost(r0, j - 1) { best = best.min(c as i64 - self.v[j]); }
    }
    (best != i64::MAX).then(|| (total as i64 - self.u[r] + best).max(0) as u64)
}

Measured: identical optimal push counts, 3 more Microban levels for backward alone, faster on 3 of 4 sets, and SokHard portfolio 117/116 against 114/116.

Memory mattered. The first warm-start version stored 3(m+1) 64-bit values per node, about 900 bytes at 36 boxes, and long runs were killed by the memory cap. Storing only v and the assignment keeps node counts identical and lasts 46% longer before the limit (src/matching.rs:100 save).

FESS over macro moves

Best-first search is weak on rearrangement puzzles: the right plan often makes the distance estimate worse first. FESS (after Festival) projects every position onto a small feature space and spreads effort across the occupied cells. Here a cell is (boxes packed according to the plan, number of free-space regions). The scheduler cycles over cells and takes one move from each per visit, so progress in any feature earns its own share of time.

src/fess.rs:92 solvesrc/fess.rs:350 pop_cyclicsrc/fess.rs:53 better
/// Feature cell: (packed boxes, free-space regions).
type Cell = (u32, u32);

/// Lexicographic feature order: more packed boxes, then fewer regions.
fn better(a: Cell, b: Cell) -> bool {
    a.0 > b.0 || (a.0 == b.0 && a.1 < b.1)
}

Advisors

Inside a cell, moves are taken by accumulated weight. Advised moves cost 0 and all others cost 1. There are three advisors: the best move that packs a box, the best move that merges free regions, and the best move that reduces the number of hotspot boxes blocking others.

Macro moves

One box pushed any number of times while the player walks freely, so depth counts box moves, not pushes. Per box, one DFS computes articulation points, which tell which sides of each square the player can walk between. It also gives each move's region count in O(1) instead of a flood fill per child. src/macros.rs:93 dfs

Completeness

Every generated move is eventually expanded unless it is a proven deadlock or a duplicate. So an empty queue proves the level unsolvable, and plans and advisors only change the order of work.

Hotspots

Box A is a hotspot if some other box could reach fewer goals were A's square a wall. This is precomputed per square, and the runtime count is O(boxes²) bit tests. src/hotspots.rs:26

Packing plans

The planner answers one question: in which order must the goals be filled? Think backward from the solved position. The goal filled last must hold a box that can still be pulled out to some starting square while every other goal is full. Removing a box only frees space, so removability is monotone. Peeling off every removable box in rounds therefore gives a layering without search, computed per cluster of adjacent goals.

src/packing.rs:150 PackingPlan::computesrc/packing.rs:283 can_leavesrc/packing.rs:229 packed

Three refinements each fixed a measured failure:

  • Per cluster, not global. An independent goal pocket landed in the last global layer and never counted as packed (XSokoban #10, then solved in 0.18 s).
  • "Can leave" means reaching a start square. On XSokoban #44 a goal sits above a niche reachable only from that goal. Pulling into it is not leaving, and this fix took XSokoban from 47 to 51.
  • Exact consistent fillings. For clusters up to 4,000 states, the plan keeps the set of fillings from which the cluster can still be completed. Layers lose order inside a layer. This gave 52 and ran 30% faster.

Orders cannot express parking: moving a box out of the goal area into a niche and back later. XSokoban #44 fills its 3×3 goal block this way. retro.rs solves a relaxed backward problem with macro pulls, where other boxes are ignored and a box reaching a start square disappears. That yields a step-by-step plan in milliseconds, and when the plan parks boxes, FESS measures progress along it instead (52 → 59).

Exact dead-set tables

Take any k boxes alone on the board with the player in some region. If even they cannot all reach goals, the full position is dead too, because removing boxes only makes a position easier. Which (box set, player region) states can be finished is computed once per level by breadth-first pulls from every all-on-goals state. Anything not reached is a deadlock.

The mirror table, seeded from start squares and expanded by pushes, prunes the backward searches. Seeding it only from the start player's own region was a free, sound gain suggested by Codex.

From src/deadsets.rs:308. In a one-wide corridor the rear box cannot move until the front one does, and the player can never reach the front one's far side. Neither box is frozen and the matching is feasible, so only the pair table catches it.

Partner filtering

Table lookups for every child were the largest per-child cost. Each square now keeps a bitset of the squares it appears with in any dead set. A moved box can only complete a dead set with its partners, usually none, so most checks exit at once. This took SokHard from 89 to 98. src/deadsets.rs:232 moved_box_dead

How the tables are kept honest

  • Exhaustive agreement with brute-force solving on small boards (src/deadsets.rs:355).
  • Every position along real solutions must be alive in both directions (src/deadsets.rs:405). This test was added after a refactor bug made the backward tables reject everything.

Portfolio and safety

The four strategies were chosen by measuring each one's unique solves and then head-to-head on every pack. Solo strength is not portfolio value. Weighted backward alone beat optimal backward 70 to 61, but replacing it dropped the portfolio from 97 to 87. Running both is what won.

// src/main.rs:38
const DEFAULT: [Strategy; 4] =
    [Strategy::Optimal, Strategy::Fess, Strategy::Backward(1), Strategy::Backward(3)];

Only solutions stop the race

Solutions are verified by replay; "unsolvable" verdicts are not. A buggy table once made one thread claim every SokHard level unsolvable, and the whole portfolio collapsed to 1/163. Now a verdict only ends its own thread, and a later solution prints a soundness warning. src/main.rs:85

Memory watchdog

A background thread polls resident memory from /proc/self/status. At the limit (default half of RAM, --memory-limit) it stops every search, which then reports a timeout. src/main.rs:131

Optimal when possible

Earlier strategies win ties, and A* is first. So a reported solution is push-optimal whenever A* finished within the budget.

Time-bound or guidance-bound?

The same levels that failed at 10 s were rerun at 60 s. If six times the time solves most of them, the pack is time-bound and engine speed pays. If not, the search needs better guidance or dead-end recognition.

How things were measured

The rules the user set: think from first principles, measure on real level packs, don't cargo-cult other solvers, and keep a technique only if the default portfolio solves more pack levels. On ties, the simpler code wins. Every technique goes in EXPERIMENTS.md, kept or not.

  • Packs. Microban I–IV (493), XSokoban (90), and from the Large Test Suite: SokHard (163), Holland (81), Sasquatch (50), Grigr2001 (100), SokEvo (107). The LTS sets were not used for tuning until measured.
  • Noise. The same build measured 94, 97 and 98 on SokHard. A/B runs are interleaved (A, B, A, B) and repeated.
  • Deterministic checks. Search changes are also compared at fixed node budgets. A pure speed-up must reproduce identical node counts, then is judged by time.
  • Optimality guard. Any pruning rule must leave optimal push counts unchanged, level by level, on all four Microban sets.
  • Machine safety. Every run goes through a harness that takes a file lock (one CPU-heavy job at a time) and runs under a 3 GB cgroup with no swap.

Lessons encoded in the code

  • The freeze checker's treat-as-wall marks must be scoped to the recursion path. Stale marks cause false deadlocks.
  • Single-row re-augmentation of a rectangular Hungarian problem is only sound with square padding.
  • A corral verdict must be cached per region. One fence can enclose regions with different verdicts.
  • Unreachable * squares are decorative and must be dropped, not rejected (Microban 1 #155).
  • Some of the hand-written test expectations were wrong while the tables were right. Tests now use exhaustive search or real solutions as the oracle.

Where it stands

  • The local working branch learned-deadlocks was merged into main. Its name was a leftover (that idea was ruled out).

Open measurement

Player-aware distances: optimal pushes are identical on all Microban sets, and it was faster on 3 of 4. SokHard is inconclusive: 114 against a baseline of 103 measured while the machine was swapping. It needs the interleaved SokHard/Holland/XSokoban A/B rerun, about an hour.

Open problems

  • Large levels (XSokoban 67/90, Holland 61/81) are not time-bound. FESS's best positions on misses are provably dead, so the lever is recognizing dead ends early. Learned deadlock patterns work in principle, but proofs cost 2–30 s each.
  • Dense levels (SokHard, Sasquatch): SokHard is time-bound, so backward speed still pays. Sasquatch is memory-bound.
  • Reinforcement learning only after the classical techniques are exhausted, and only as an advisor inside FESS, never as a pruner.
