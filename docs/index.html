Sokoban Solver Field Notes

A reference for the Rust solver in rkirov/sokoban-ai: what each part does, why it is there, how it stays correct, and where it lives in the code. At 10 seconds per level it solves 490 of 493 Microban levels and 158 of 163 SokHard levels, more than YASS, Festival and Takaken report on that pack. Given 40 seconds it solves all of SokHard.

~5,700 lines of Rust in src/ 36 tests One dependency (rustc-hash) Code pointers link to commit 5135344

At a glance

The solver runs four different searches at the same time, one per thread, and reports the first solution that replays correctly against the original level. Each search is strong on a different kind of level:

  • Forward A* finds push-optimal solutions on small and medium levels.
  • FESS (feature-space search over whole-box moves, guided by a packing plan) handles large levels that need a plan.
  • Backward search starts from the solved position and pulls boxes. Levels cramped around their goals are easy in this direction. It runs twice, both times greedy: once over single pulls and once over macro pulls, where one box is pulled any distance.

All four share one board model, one lower bound (a min-cost matching of boxes to goals), and a stack of deadlock detectors. Every detector is sound: it never declares a solvable position dead.

Sokoban for solvers

A position is the set of box squares plus where the player is. Two positions where the player can walk to the same squares behave identically, so the player is named by the smallest square index in its reachable region. The pair (sorted boxes, region name) is the key of every transposition table in the solver.

The unit of cost is a push. Walking between pushes is free and is reconstructed only at the end: src/verify.rs:13 fills in the walks with a breadth-first search, and src/verify.rs:91 replays the full move string against the original level text. Nothing is reported without passing that replay.

Three ideas carry the work:

  • Lower bounds. An optimistic count of pushes still needed. It orders A* and proves a position dead when it is infinite.
  • Deadlocks. Positions that can never be solved. Each one detected removes a whole subtree.
  • Search shape. Which positions to look at first. Most hard levels are lost here, not to raw speed.

Below is the solver's own solution to XSokoban #1, 97 pushes found in 31 ms. Lowercase letters in its output are walks and uppercase letters are pushes.

Architecture

A level is parsed into a Board. Each strategy builds the per-level tables it needs, then all four strategies race with the full time budget. The first solution stops the others and is verified by replay.

The board

Board::from_level turns level text into squares the player can ever reach, numbered 0..n, with a four-neighbour table. Everything else becomes wall. Short rows are padded with wall. A * the player can never reach is a decorative box already on its goal, so it and its goal are dropped.

Distance tables and dead squares

Each goal gets a table of relaxed push distances: how many pushes a lone box needs to reach that goal if the player could teleport to any floor square. The table is built backward from the goal as pulls. A box at q can be pulled to a neighbour n when n and the square beyond it are both floor. Squares from which no goal can be reached are dead, and no push onto a dead square is ever generated.

A mirror table, start_dist, gives the push distance from each start box to every square. The backward search uses it as its lower bound, and squares no start box can reach are dead for that search.

Symmetries

The board finds its automorphisms: the mirror and rotation transforms of the bounding rectangle that preserve floor and goals. Forward A* and FESS key positions by the smallest image under those transforms, so symmetric positions are searched once. The backward search must not do this, because symmetries preserve goals but not start squares; a test pins it.

src/level.rs:113 canonical_keysrc/tests.rs:236

Gate pushes

A box pushed onto a non-goal square can seal the pushing side off from the box's other sides, counting walls only. When it does, the only useful next move for that box is to keep pushing it forward, so forward A* generates only that push. The rule depends on the position alone, which makes it safe with a transposition table.

Forcing boxes through every wall-flanked corridor would be simpler, but it is unsound. In Microban 1 #10 below, a box must be parked inside such a corridor so the player can pass. The test src/tests.rs:195 keeps that level solvable.

The lower bound

Every box must end on a different goal, so the pushes still needed are at least the cheapest way to assign boxes to distinct goals, using the distance tables as costs. That is a min-cost bipartite matching, solved with the Hungarian algorithm (Jonker-Volgenant style, with potentials). If no complete assignment exists, some box can reach no free goal and the position is dead.

src/matching.rs:24 Matchersrc/matching.rs:72 solve

A push changes one box, which is one row of the cost matrix. The matcher exploits this in three ways.

One-row re-solve

From a solved state, only the changed row is re-augmented: O(m²) instead of O(m³). This is exact only if rectangular problems (fewer boxes than goals) are padded to square with zero-cost dummy rows. src/matching.rs:161 resolve_row

Saved states

The backward search stores each node's column potentials and assignment (2(m+1) small numbers). A child reloads them, recomputes row potentials from complementary slackness, and re-solves one row. src/matching.rs:100 save

O(m) dual bound

Children are queued with a cheaper bound. Keep the parent's duals and replace only the moved row's potential by that row's minimum reduced cost. The duals stay feasible, so by weak duality the dual objective is a lower bound. src/matching.rs:134 row_lower_bound

// src/matching.rs:134   LB = total − u_r + min_j (c'_rj − v_j)
pub fn row_lower_bound(&self, r0: usize, total: u64, cost: impl Fn(usize, usize) -> Option<u32>) -> Option<u64> {
    let r = r0 + 1;
    let mut best = i64::MAX;
    for j in 1..=self.m {
        if let Some(c) = cost(r0, j - 1) { best = best.min(c as i64 - self.v[j]); }
    }
    (best != i64::MAX).then(|| (total as i64 - self.u[r] + best).max(0) as u64)
}

Boxes frozen on goals tighten the bound further. Their matching rows are locked to the goal they sit on, and the distance tables are recomputed with them as walls, cached per frozen set. That catches the common stall where every box but one is packed and the frozen boxes seal off the last goal.

Freeze deadlocks

A box is blocked along an axis when a wall is on either side, when dead squares are on both sides, or when a neighbour on that axis is itself blocked along the other axis. The recursion treats boxes already on its path as walls: in a cycle of mutual blocking, no box can be the first to move. A box blocked on both axes is frozen, and frozen off a goal means dead. The wall marks must be scoped to the recursion path, or stale marks cause false deadlocks.

src/deadlock.rs:64 is_freeze_deadlocksrc/deadlock.rs:31 scan_frozensrc/tests.rs:146

Exact dead-set tables

Take any k boxes alone on the board with the player in some region. If even they cannot all reach goals, the full position is dead too, because removing boxes only makes a position easier. Which (box set, player region) states can be finished is computed once per level, by breadth-first pulls from every state with all k boxes on goals. Every state not reached is a deadlock. Pairs are built for levels up to 400 squares and triples up to 120.

The mirror table serves the backward searches. It is seeded from the start squares with the player in the start player's region, and expanded by pushes. A box set it never reaches could not have come from the start position.

Checking a child costs one lookup per combination with the moved box, which used to be the largest per-child cost. Each square therefore keeps a bitset of partner squares, the squares it appears with in some dead set. A moved box can only complete a dead set with its partners, so most forward checks exit immediately. Backward tables are much denser: nearly every pair of squares is partnered. For triples, each ordered pair of squares therefore also keeps a bitset of the third squares that complete a dead triple. The check ANDs that with the occupied partner squares and looks up only the hits. This made the backward search 1.4–1.8× faster with identical results.

PI-corrals

A corral is an area the player cannot reach, fenced by walls and boxes. Suppose that, with every box outside the corral removed, each possible push of a fence box goes into the corral and could be made right now. Then any solution can be reordered so that such a push comes first. If the corral is unfinished (a fence box off its goal, or an empty goal inside when every goal must be filled), the search only needs to try those pushes at this node. This keeps push-optimality.

An unfinished corral with no possible push can never change, so the position is dead. Corrals that fail the conditions get a capped mini-search on the reduced board (at most 10 boxes, 400 states). It aborts with "not proven" if the fence opens, a box leaves the corral's area, or an outside box could be pushed in. Otherwise, exhausting every state without resolving the corral proves a deadlock. Verdicts are cached per corral, keyed by its region, because one fence can enclose several regions with different verdicts.

src/corral.rs:96 analyzesrc/corral.rs:200 qualifysrc/corral.rs:315 mini_deadlock_searchsrc/tests.rs:267

Grown corrals. When no corral passes, the A* search grows one instead of giving up (re-derived from YASS). Starting from an unreachable area next to a box the player can reach, each push of a corral box is checked. If the player's square for it is another unreachable area, or the push goes into one, that area is merged: the conditions above do not need the corral to be connected. If an outside box stands on the player's square, it joins the corral when it can step aside (its neighbours across the push are free), so its pushes are tried too; if it cannot, the push is impossible and ignored, as is a push that would freeze the box among corral boxes. Only a push from a reachable square onto reachable floor rejects the corral. Optimal push counts stay the same on all of Microban, and SokHard goes from 153–154 to 158 solved.

The four searches

Forward A*

Best-first search over pushes, ordered by f = g + h, with the matching as h. The bound is consistent (it changes by at most 1 per push), so the first time a position is popped it has its shortest push count, and duplicates can be dropped when popped. Queue entries are only (parent, box, direction); a child is built and checked only when popped. Keys are small integers, so an array of buckets (by f, then h, newest first) replaces a binary heap.

src/solver.rs:169 solvesrc/solver.rs:118 BucketQueue
  1. Materialize the child from its parent and push, and flood the player's region.
  2. Transposition check with the symmetry-canonical key; drop the entry if this position was already reached with no more pushes.
  3. Goal test, then pick candidate pushes: only the forward push after a gate push, only the corral pushes when a PI-corral exists, or all pushes. A corral deadlock ends the node.
  4. Node checks. Scan for frozen boxes (a frozen box off a goal kills the node), recompute distances with frozen-on-goal walls if any, and solve the matching once.
  5. Children. For each push to a live square with the pushing side reachable: freeze check, dead-set check, then one-row matching re-solve for the child's h.

Backward search

The backward search starts from the solved position (one root per player region of the goal-filled board) and pulls boxes until they sit on the start squares with the player connected to the start. Its bound is the matching over start_dist, and its pruning uses the backward dead squares and the mirror dead-set tables. It returns forward pushes by reversing the path.

The search can run optimally (f = g + h), weighted, or greedily (f = h); the portfolio runs it greedily, twice. The two orderings solve different levels: greedy dives straight for the start position and solves many crowded levels the optimal search cannot finish, An optimal backward thread used to cover levels where greedy gets lost; a second greedy thread over macro pulls turned out to be worth more (below). The greedy search expands each position once: its ordering ignores the push count, so re-expanding a position reached again by a shorter path would only repeat work. That one rule took SokHard from about 123 to 146.

The second greedy thread moves boxes with macro pulls: one box pulled any number of steps while the player walks freely, the same move shape FESS uses forward. Search depth then counts box moves instead of single pulls, which helps on large levels with long corridors. Alone it is much weaker on SokHard (112 levels against 152), but it solves levels nothing else does, such as XSokoban #14. A solution's macro pulls are expanded back into single pulls from each parent position before the answer is replayed. src/macros.rs generate_pulls, unit_pulls

src/solver.rs:492 solve_backward
  1. Materialize. Copy the parent's boxes in parent order and move one. Keeping the order means matching row i is still box i. A sorted copy is used as the key.
  2. Flood the player region and name it by its smallest square.
  3. Duplicate check against the transposition table, keyed by raw boxes (no symmetry merging).
  4. Exact bound. Load the parent's saved matching and re-solve the moved row.
  5. Requeue if the bound rose. The entry was queued with the O(m) dual bound. If the exact value is higher it goes back in at its true key; nothing has been stored yet.
  6. Store and expand. Save the matching state, test for the start position, and generate pulls. Filter by backward dead squares and dead sets, then queue each child with its dual bound.

FESS over macro moves

Best-first search is weak on large rearrangement puzzles: the right plan often makes the distance estimate worse before it gets better. FESS (after Festival) maps every position to a small feature cell, here (boxes packed according to the plan, number of free-space regions). It then cycles over the occupied cells, taking one move from each per visit, so progress in any feature gets its own share of time. A child that is worse than its parent's cell stays in the parent's cell instead of opening a worse one.

src/fess.rs:147 solvesrc/fess.rs:410 pop_cyclicsrc/fess.rs:53 better
/// Feature cell: (packed boxes, free-space regions).
type Cell = (u32, u32);

/// Lexicographic feature order: more packed boxes, then fewer regions.
fn better(a: Cell, b: Cell) -> bool {
    a.0 > b.0 || (a.0 == b.0 && a.1 < b.1)
}

Macro moves

A move is one box pushed any number of times while the player walks freely, so search depth counts box moves, not pushes. For each box, a breadth-first search over (box square, player side) finds every destination. One depth-first search per box finds articulation points, which say which sides of each square the player can walk between, and give each move's region count in O(1). src/macros.rs:285 generate

Advisors

Inside a cell, moves are taken by accumulated weight. Advised moves cost 0 and all others cost 1. The three advisors pick the best move that packs a box, the best move that merges free regions, and the best move that reduces the number of hotspot boxes. src/fess.rs:147

Pruning

Positions chosen for expansion get the full checks: corrals, frozen boxes, and the matching with frozen walls. Each child gets the cheap ones: freeze and dead sets.

Fair lines of play

Every queued move belongs to a line: the first move from the start position on its path. Within a cell, lines are served round-robin. Without this, the first line to reach a cell floods it with advised (weight 0) moves and the others starve. On XSokoban #28 the right first move parks a box in a niche, gains nothing the features can see, and used to starve; now it is solved in 2 s. src/fess.rs:104 CellQueue

Completeness

Every generated move is eventually expanded unless it is a proven deadlock or a duplicate. So an empty queue proves the level unsolvable. Plans and advisors only change the order of work.

Plans and advisors

Packing order

The planner answers one question: in which order must the goals be filled? Think backward from the solved position. The goal filled last must hold a box that can still be pulled out to a starting square while every other goal is full. Removing a box only frees space, so removability is monotone. Peeling off every removable box in rounds gives a layering without search. Reversed, the rounds are the packing layers.

  • Per goal cluster. Layers are computed per group of adjacent goals with the other clusters empty. A global layering puts independent goal pockets in the last layer, where they never count.
  • "Leave" means reaching a start square. Being pulled to just any non-goal square is not enough. On XSokoban #44 a goal sits above a niche reachable only from that goal.
  • Exact tables for small clusters. Up to 4,000 states per cluster, the plan keeps every filling from which the cluster can still be completed. "Packed" is then the largest such subset of the current filling, which keeps order information that layers lose.
src/packing.rs:150 computesrc/packing.rs:283 can_leavesrc/packing.rs:229 packed

Relaxed plan with parking

An order over goals cannot express parking: moving a box out of the goal area into a niche and bringing it back later. The relaxed plan solves a simpler backward problem: from the solved position, pull boxes with macro pulls, ignore all other boxes, and remove a box once it reaches a start square. When some box can be removed, only removals are generated, which keeps branching tiny. The result is a step-by-step plan in milliseconds. When that plan parks a box, FESS measures progress along the plan instead of the packing order.

Hotspots

Box A is a hotspot if some other box could reach fewer goals were A's square a wall. Such boxes usually have to move before the boxes behind them can be packed, and the packing count cannot see that. The effect of every blocker square is precomputed per level, so counting a position's hotspots is O(boxes²) bit tests. The count drives an advisor and a tie-break in FESS.

Portfolio and safety

Only solutions stop the race

Solutions are verified by replay, but "unsolvable" verdicts cannot be. A verdict therefore ends only its own thread, so one unsound strategy cannot stop the others. If a solution appears after another thread claimed "unsolvable", the program prints a soundness warning. src/main.rs:94 solve_auto

Optimal when possible

Earlier strategies win ties and forward A* is first. So a reported solution is push-optimal whenever A* finished within the budget.

Memory watchdog

A background thread polls resident memory from /proc/self/status. At the limit (default half of RAM, or --memory-limit) it stops every search, which then reports a timeout instead of exhausting the machine. FESS also caps its queue at 20 million moves. src/main.rs:140

Why these four

Each strategy was measured for the levels only it solves, then head-to-head on every pack. The two greedy backward threads differ only in move shape, yet each solves levels the other cannot: single pulls dominate SokHard, macro pulls reach levels like XSokoban #14. They replaced an optimal and a weighted backward thread, gaining SokHard, Sasquatch, XSokoban and Microban levels.

Limits and next steps

The levels failed at 10 s were rerun at 60 s. If six times the time solves most of them, the pack is limited by speed. If not, the search needs better guidance or better recognition of dead ends.

Large levels

XSokoban (70/90) and Holland (62/81) are not limited by time. On most XSokoban misses FESS reaches a near-complete position that is already dead, and the fatal move happened many moves earlier, for example a box plugging the only door to the goal room. The rest stall early because the plan gives no sense of progress (diagonal goal rooms, parking plans). Festival-style learned deadlock patterns were built and measured, but their proofs did not succeed within a useful budget here.

Dense levels

SokHard is limited only by time: every level is solved within 40 s, almost all by the greedy backward thread, so its speed converts directly into solves. Sasquatch runs into the memory cap after 25–50 s.

Reinforcement learning

Only after the classical techniques are exhausted, and only as an advisor inside FESS, never as something that prunes.

Candidate: player-aware distances

The distance tables let the player teleport. A tighter version tracks which side of the box the player is on. After a push the player stands where the box was, and can only reach box sides connected to that square without passing through the box. The bound stays a lower bound and can only get tighter. It changes the tables on 70 of 163 SokHard levels and finds new dead squares on 27. It is implemented on the local branch player-aware-dists, with identical optimal solutions on all of Microban. Whether it solves more levels has not been measured yet.

Computed in the browser with both rules. The box has to turn the corner at the end of the corridor, pushed down from the one-square niche above the corner. The relaxed rule lets the player teleport into the niche and says 4 pushes. The player can only reach that niche through the corner square the box would be standing on, so the player-aware rule marks the box's square dead (outlined).
